## Goal

Implement the **Builder Specialist** (and supporting frontend/backend concerns) that consumes:
- `SiteUnderstanding`
- `SiteArchitecture`
- `ContentRecommendation` (with `chosen_variant` already decided)

and produces a production-ready, non-boilerplate modern frontend + backend implementation.

Key quality requirements:
- Beautiful, seamless, well-constructed frontends (avoid boilerplate/agentic slop)
- Explicit branding system (colors, fonts, typography, spacing) chosen and recorded
- Full use of the chosen content variant (A or B) from Marketing
- Integration of visual/frontend quality tooling (Impeccable + Lighthouse + accessibility)

## Input to Builder

The Builder receives three artifacts:

1. **SiteUnderstanding** — full scraped content, components, text, images, navigation, contact, raw text_content
2. **SiteArchitecture** — target stack, component inventory with `file_path` + `props_schema`, deployment spec, architecture decisions
3. **ContentRecommendation** — `chosen_variant`, `tone_of_voice`, `page_strategies`, `final_rationale`, `brand_preservation_notes`

**Gap identified:** No explicit **Brand / Design System** spec (primary/secondary colors, typography scale, spacing, radius, shadows, motion tokens). This must be added.

## Proposed Architecture

### Option A (Recommended): Single Builder Specialist + Internal Sub-Personas

- One `builder_specialist.md` persona that reasons about the entire build.
- Internally delegates to mental models of:
  - Frontend Engineer (React/Next.js + Tailwind + component system)
  - Backend Engineer (API routes, forms, email, data layer)
  - Design Systems Engineer (tokens, theming, accessibility)
- Uses Impeccable (or equivalent) as a polishing tool after initial generation.
- Keeps the specialist count low while still addressing FE/BE separation in reasoning.

**Why this wins:** Matches the validated "Agentic Specialist Pattern". Kilo handles the complexity. One persona = simpler orchestration.

### Option B (Alternative): Separate FE + BE Specialists

- `frontend_specialist.md`
- `backend_specialist.md`
- Conductor routes between them after Builder produces high-level plan.
- More granular but increases orchestration surface.

**Decision:** Start with Option A. Revisit Option B only if single persona produces consistently weak FE or BE output after 2–3 real builds.

## Branding & Design Tokens (Critical Addition)

**Problem:** Current `ContentRecommendation` has voice/tone but no visual design system. This leads to boilerplate or inconsistent branding.

**Solution:** Extend `ContentRecommendation` with a rich `BrandSpec` object produced by the Marketing Specialist as part of its final chosen-variant output.

Proposed richer `BrandSpec`:

```python
class BrandSpec(BaseModel):
    # Core palette
    primary_color: str
    secondary_color: str
    accent_color: str
    background_color: str
    text_color: str

    # Semantic tokens (recommended)
    semantic_tokens: Dict[str, str] = Field(default_factory=dict)  # surface, on-surface, primary-container, etc.

    # Typography
    font_family_heading: str
    font_family_body: str
    font_size_base: str
    type_scale: Dict[str, str] = Field(default_factory=dict)

    # Spacing & shape
    spacing_scale: Dict[str, str] = Field(default_factory=dict)
    border_radius: str

    # Elevation & motion
    shadow_scale: Dict[str, str] = Field(default_factory=dict)
    motion_philosophy: Literal["subtle", "energetic", "classical", "monastic"] = "subtle"
    motion_duration: str
    motion_easing: str

    # Component system
    component_variants: Dict[str, List[str]] = Field(default_factory=dict)  # e.g. {"button": ["primary", "secondary", "ghost"]}

    # Dark mode
    dark_mode_strategy: Literal["full_tokens", "auto_invert", "none"] = "full_tokens"

    notes: str = ""
```

This turns `BrandSpec` into a true **Design System Contract** that the Builder can enforce programmatically.

**Where it lives:**
- Marketing Specialist produces `brand_spec` as part of its final output (after choosing variant).
- Or run a tiny follow-up "design_tokens" specialist that only emits `BrandSpec` from the chosen variant + SiteUnderstanding visuals.

**Recommendation:** Add `brand_spec: BrandSpec` directly into `ContentRecommendation` so the Builder always has one canonical source of truth for both content tone and visual identity.

## Frontend Quality & Impeccable Integration

**Requirement:** Frontends must not look agentically generated.

**Tool:** Impeccable (https://impeccable.style/) — open-source visual quality tool for agentic frontends.

**Integration strategy (Recommended): Post-generation `ui_polish` skill with direct modification**

- Create a reusable `ui_polish` skill (or MCP binding) that any specialist can invoke.
- Default flow: **Generate → Polish → Final output**.
- The `ui_polish` skill is **allowed to directly modify** the generated component and page code (adjust spacing classes, add micro-interactions, fix contrast, apply BrandSpec tokens, enforce motion philosophy, etc.).
- Every change made by `ui_polish` must be logged in the `BuildManifest` (e.g., “Changed gap-4 → gap-6 on ServicesGrid”, “Added 200ms opacity + translateY transition to match ‘monastic’ motion philosophy”).
- This keeps the final output production-ready while maintaining full auditability for the Project Manager.

The Builder persona stays focused on architecture, component logic, and brand application. The polish pass owns visual excellence. The Builder may invoke the skill internally, but the explicit two-stage flow is the default.

## Output Contract (What Builder Produces)

The Builder produces **both** in a single Kilo call:

1. A rich, structured, auditable `BuildPlan` (excellent for Project Manager visibility, Debate Arena, and future self-critique loops).
2. The actual production-ready code files (components, pages, `globals.css` with full BrandSpec tokens applied, `tailwind.config`, forms, etc.).

This gives traceability + real code without the context loss of a separate OpenCode handoff. Kilo generates the plan and then immediately executes it.

Alternative (lower risk): Builder outputs a rich `BuildPlan` JSON that a separate codegen step (OpenCode) then executes. This keeps the Builder focused on architecture + quality decisions.

**Recommended:** Builder produces both:
- `BuildPlan` (structured spec for audit)
- Actual generated files (via Kilo + Impeccable polish)

## Creative Enhancements (Long-Term Leverage)

### A. Build Manifest as First-Class Artifact

Every generated site should produce a `build_manifest.json` that travels with the artifacts:

```json
{
  "migration_id": "uuid",
  "source_understanding_id": "...",
  "source_architecture_id": "...",
  "chosen_variant": "A",
  "brand_spec": { ... },
  "fidelity_score": 0.94,
  "build_timestamp": "...",
  "personas_used": ["builder_specialist_v1.2"],
  "impeccable_passes": 2,
  "lighthouse_scores": { "performance": 98, "accessibility": 96, ... }
}
```

This becomes extremely valuable for the Project Manager when analyzing "what worked" and proposing persona or routing improvements.

### B. Self-Critique Loop Inside Builder (Dual-LLM Quality Control)

After the initial generation pass, the Builder persona runs a lightweight internal critique:

> "Review the generated hero component against the BrandSpec and the monastic/classical ethos of St. Joseph the Worker Academy. Suggest 2–3 concrete improvements for visual weight, typography hierarchy, and emotional resonance."

This is cheap (one extra prompt step) and dramatically reduces "agentic slop."

### C. Component Semantic Graph (Future Stretch)

Instead of a flat list, the Builder can optionally emit a small relationship graph:

```json
{
  "components": [...],
  "relationships": [
    { "from": "CurriculumGrid", "to": "SubjectCard", "type": "contains" },
    { "from": "Hero", "to": "Navbar", "type": "depends_on" }
  ]
}
```

Useful for future re-architecture, A/B testing, or dynamic layout experiments.

# Builder Specialist

**Version:** 1.0
**Status:** Phase 3 — Builder + Polish
**Role Type:** Persona / Full-Stack + Design Systems Charter

---

## Role Overview

You are a senior full-stack engineer and design systems thinker. Your job is to take a `SiteUnderstanding`, `SiteArchitecture`, and `ContentRecommendation` (with chosen variant and rich `BrandSpec` already decided) and produce a production-ready, beautiful, non-boilerplate implementation.

**Core Principle:** Never output generic agentic code. Every component must feel custom to the brand, emotionally resonant, and technically excellent. Use the `ui_polish` skill liberally.

---

## Charter

1. **Consume the full input set**
   - `SiteUnderstanding` for content, structure, and raw text
   - `SiteArchitecture` for component inventory, file paths, props schemas, and architecture decisions
   - `ContentRecommendation` for chosen variant, tone, page strategies, and `BrandSpec`

2. **Apply the BrandSpec as the single source of truth**
   - Use semantic tokens, component variants, motion philosophy, and dark mode strategy everywhere.
   - Translate `motion_philosophy` into concrete code:
     - `monastic` → very restrained (200–300ms fades, opacity + translateY only, no scale)
     - `classical` → elegant (400ms ease-out, subtle 1.02 scale on hover, gentle spring on modals)
     - `energetic` → bolder (150ms, scale + shadow elevation, micro-bounce on CTAs)
     - `subtle` → minimal tasteful motion

3. **Generate production-grade code**
   - Build real, typed components (not stubs)
   - Wire forms to match captured fields + validation
   - Apply image strategy and content from the chosen variant
   - Ensure responsive, accessible, and performant output

4. **Run the polish pass**
   - After initial generation, invoke the `ui_polish` skill.
   - Allow it to directly modify code for visual excellence.
   - Log every change made by polish into the `BuildManifest`.

5. **Perform structured self-critique**
   - After polishing, run an internal critique pass.
   - Output a structured block (see Self-Critique section below).
   - Store the critique in the `BuildManifest`.

6. **Produce the final artifacts**
   - Rich `BuildPlan` (auditable)
   - Actual code files
   - `BuildManifest.json` with full provenance, chosen variant, BrandSpec, polish logs, self-critique, and scores
